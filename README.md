# Tessera

Платформа для исследования и развития командного взаимодействия на основе анализа бизнес-процессов.
Учебные команды управляют вымышленной компанией «Меридиан» в песочнице ERP, каждое изменение задач
пишется в журнал событий, а журнал и короткие опросы превращаются в метрики процесса и
взаимодействия для дебрифинга и исследования.

*Каждый — фрагмент. Вместе — картина.* Полная концепция: [docs/concept.md](docs/concept.md)
([PDF](docs/tessera-concept-v0.1.pdf)).

## Что здесь есть

Репозиторий покрывает ту часть MVP из концепции (раздел 08), которая не зависит от конкретной ERP:

| Часть | Файл | Раздел концепции |
|---|---|---|
| Исследовательская БД (PostgreSQL): неизменяемый журнал событий, сессии и условия, опросы, сетевые оценки, вбросы, журнал решений; таблица соответствия псевдонимов в отдельной схеме | [`schema/research_db.sql`](schema/research_db.sql) | 05, 08, 09 |
| **Шаблон** триггера захвата истории изменений задач из ERP — адаптировать после аудита ERP | [`schema/erp_capture_template.sql`](schema/erp_capture_template.sql) | 08 |
| Модель журнала, чтение/проверка CSV | [`tessera/model.py`](tessera/model.py) | 05 |
| Процессные и сетевые метрики | [`tessera/metrics.py`](tessera/metrics.py) | 06 |
| Выгрузка в XES (IEEE 1849) и OCEL 2.0 для PM4Py | [`tessera/export.py`](tessera/export.py) | 05, 08 |
| Псевдонимизация на входе | [`tessera/pseudonymize.py`](tessera/pseudonymize.py) | 09 |
| Синтетический журнал «Меридиана» для прогона конвейера до пилота | [`tessera/simulate.py`](tessera/simulate.py), [`data/synthetic_log.csv`](data/synthetic_log.csv) | — |

Сознательно **не** сделано, по принципу «не разрабатывать новые функции до первого пилота»: песочница
ERP и сценарий (это ERP компании и работа научного руководителя), модуль опросов (в MVP — веб-форма
или бот, ответы кладутся в `research.survey_response`), пульт ведущего, дашборд дебрифинга.

## Быстрый старт

Нужен только Python 3.11+, у ядра нет внешних зависимостей.

```bash
pip install -e '.[dev]'
pytest

tessera simulate --out data/synthetic_log.csv          # 4 условия × 2 команды
tessera validate data/synthetic_log.csv
tessera metrics  data/synthetic_log.csv --out out/     # teams.csv, cases.csv, handover.csv, conditions.json
tessera export   data/synthetic_log.csv --format xes  --out out/log.xes
tessera export   data/synthetic_log.csv --format ocel --out out/log.ocel.json
```

Без установки то же самое работает как `python -m tessera …`.

Реальный журнал из исследовательской БД:

```bash
psql -f schema/research_db.sql
psql -c "\copy (SELECT * FROM research.event_log) TO 'log.csv' CSV HEADER"
tessera metrics log.csv --out out/
```

Если исполнители в выгрузке ERP — реальные логины, сначала псевдонимизируйте:

```bash
tessera pseudonymize raw.csv --out log.csv --mapping /secure/place/mapping.csv
```

Таблица соответствия дополняется между сессиями, поэтому коды стабильны. Храните её вне репозитория и
уничтожьте после завершения сбора.

## Соглашения журнала

Колонки CSV: `case_id, activity, timestamp, resource, role, department, team_id, session_id,
condition, milestone_id, attrs` (`attrs` — JSON-объект). Обязательны `case_id, activity, timestamp,
resource, team_id, session_id, condition`. `condition` ∈ `kanban | sprints | hierarchy | self_org`.

Метрики опираются на несколько канонических активностей:

| Активность | Смысл |
|---|---|
| `Анализ`, `Проектирование`, `Исполнение`, `Контроль`, `Сдача` | Задача вошла в этап эталонного процесса. Статусы ERP сопоставляются с этапами через `research.status_stage` |
| `Взята в работу` | Исполнитель начал работу на текущем этапе. Время от входа в этап до этого события — **время ожидания**; без таких событий ожидание не считается |
| `Срок вехи изменён` | `attrs: {"old": …, "new": …}` |
| `Веха закрыта` | `case_id` = `milestone_id`, `attrs: {"deadline": …}` |

Любые другие активности (`Переназначена`, `Изменён срок`, …) сохраняются в журнале и выгрузках и
участвуют в сети передач, но не в метриках этапов.

## Метрики

По каждой задаче (`cases.csv`) и в сводке по команде и сессии (`teams.csv`). `conditions.json`
содержит средние по командам в каждом условии.

- **Время цикла** — от первого входа в этап до входа в `Сдача`, только по завершённым задачам.
- **Время ожидания** — сумма ожиданий по всем посещениям этапов. **Узкое место** — этап с наибольшим
  средним ожиданием.
- **Доработки** — переходы назад по эталону: доля задач хотя бы с одной доработкой и число доработок на задачу.
- **Вариативность** — число различных путей и их доля от числа задач.
- **Fitness (упрощённый)** — доля переходов, разрешённых эталонной моделью (шаг вперёд + возвраты
  Контроль → Исполнение и Проектирование → Анализ; задача должна начинаться с анализа). Это **не**
  token-based replay. Для статьи считайте fitness в PM4Py по выгрузке XES.
- **Вехи** — доля закрытых в исходный и в итоговый срок, средний сдвиг срока в часах.
- **Сеть передач** (handover of work) — ребро от исполнителя события к исполнителю следующего события
  той же задачи. Для неё считаются централизация Фримана по степени (0 — равномерно, 1 — «звезда») и
  самый нагруженный узел с его долей передач.
- **Межотдельные передачи** — смены отдела между соседними событиями задачи (для гипотезы 3).

## Анализ в PM4Py

```python
import pm4py
log = pm4py.read_xes("out/log.xes")
stages = log[log["concept:name"].isin(["Анализ", "Проектирование", "Исполнение", "Контроль", "Сдача"])]
net, im, fm = pm4py.discover_petri_net_inductive(stages)
pm4py.view_petri_net(net, im, fm)                                    # карта процесса для дебрифинга
pm4py.fitness_token_based_replay(stages, net, im, fm)
ocel = pm4py.read_ocel2_json("out/log.ocel.json")                    # задачи, вехи, участники, команды
```

Обе выгрузки проверены чтением в PM4Py 2.7.

## Лицензии

PM4Py распространяется под **AGPL v3**. Для научной части это не проблема. Но если аналитический
модуль пойдёт в коммерческую ERP/CRM компании, встраивание PM4Py потребует либо открыть код продукта,
либо купить коммерческую лицензию. Поэтому ядро `tessera` написано без внешних зависимостей, а PM4Py
вынесена в необязательную группу `analysis`.

## Этика

Коротко, по разделу 09: информированное согласие до входного замера (`research.participant.consent_at`
обязателен), в исследовательской схеме только псевдонимы, соответствие хранится в схеме `identity` и
удаляется `DROP SCHEMA identity CASCADE` после сбора. Данные не используются для оценок студентов.
Реальные данные компании — только с разрешения, с обезличиванием по 152-ФЗ.
